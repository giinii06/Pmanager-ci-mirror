# 스캔 및 런타임 성능 벤치마크 보고서

모든 수치는 추정치가 아닌 실측 결과입니다. 로컬 합성 측정은 `scripts/bench-scan.ts`를 사용했고, 실서버 측정은 Win11 호스트(`192.168.0.27`, WSL2 Ubuntu 24.04)의 Docker 컨테이너 내부에서 실행했습니다.

## 1. 병목 원인 및 최적화 내용

1. **워처 파일 전수 `stat` 폴링 제거 (`apps/worker/src/watch.ts`)**: 기존 `chokidar`가 `/media` 전체(추가된 `C:\`, `D:\`, `E:\` 마운트 및 `WATCH_POLLING=1` 13,080개 파일)를 수 초마다 전수 `stat()`해 유휴 상태에서도 CPU 63–98%, RSS 713.7 MiB를 점유하던 문제를 등록 라이브러리 한정 디렉터리 `mtime` 폴러로 대체했습니다.
2. **단일 패스 `Dirent` 재사용 (`scan.ts`, `packages/media/src/archive.ts`)**: 디렉터리 내 중복 `readdir`를 제거하고 이미 읽은 `Dirent[]`를 아카이브 탐색에 재사용했습니다.
3. **사전 1회 인덱스 로드 + `O(1)` 맵 갱신 + 250건 WAL 배치**: `preloadLibraryScanIndex`로 기존 에셋 맵을 1회 적재하고, `flushBatch`에서 `PRAGMA synchronous = FULL` 상태로 250건씩 일괄 커밋했습니다.
4. **제한된 비동기 `stat`/프로브 풀**: `STAT_CONCURRENCY = 16`, `IMAGE_PROBE_CONCURRENCY = 8`, `VIDEO_PROBE_CONCURRENCY = 4`로 DrvFS(9P) I/O 지연을 병렬화했습니다.

## 4. Rust 사이드카 미도입 결정 근거

Win11 `D:\` DrvFS 실측에서 1,000개 `stat(16)`은 `137 ms`, `enum`은 `111 ms`인 반면 9P 파일 열기 기반 프로브가 `5,525 ms`를 차지했고, 13,080개 실제 라이브러리 증분 스캔이 Bun + TypeScript만으로 `3.43초`에 완료되었습니다. 병목은 Bun CPU나 GC가 아니라 DrvFS 9P 파일 열기 레이턴시이므로 별도 Rust 바이너리를 도입하지 않고 단일 TS 런타임을 유지했습니다.

### 6.3 장면 정확 스캔 대안 (100,000 장면)

같은 100,000장면 DB(300,000 임베딩)에서 네 구현을 **교대 실행**으로 5회 × 10회 측정했습니다. 한 구현을 연속 측정하면 페이지 캐시가 그 구현에 유리하게 데워지므로, 회차마다 순서를 바꿨습니다. 측정 시 머신 부하가 높아 절대값은 부풀려져 있고, 순위와 배율만 신뢰합니다.

| 구현 | p50 | p95 | 현재 구현과 동일 |
| --- | ---: | ---: | --- |
| 현재 (`scene_embeddings` → `video_scenes` 조인, `ORDER BY scene_id, modality`) | 807 ms | 968 ms | 기준 |
| A: 메타데이터 `Map` + 정렬된 임베딩 스캔 | 717 ms | 770 ms | 예 |
| B: 정렬된 스캔 + 해시, top-K 없음 | 664 ms | 726 ms | 예 |
| E: 비정렬 스캔 + 해시 + `dot4` + top-K (`scripts/bench-search.ts`의 `variantSceneScan`) | **520 ms** | **641 ms** | 예 (점수 차이 2.4e-15) |
| E, 라이브 규모 (12,851장면) | 60 ms | 63 ms | 예 (현재 92/97 ms) |

- 병목은 자료구조가 아니라 I/O와 산술입니다. `ORDER BY scene_id, modality`만으로 257 ms가 들고(정렬 제거 시 602 → 345 ms), 조인의 문자열 키 인덱스 조회가 약 230 ms(블롭을 읽지 않는 같은 쿼리도 573 ms), 1.2 GB 벡터 읽기가 345 ms, 내적이 197 ms(`dot4`로 73 ms)입니다.
- 따라서 이 규모에서 정확 스캔의 하한은 p50 약 450 ms이며, E는 그에 70 ms 근접합니다. **500 ms p95를 넘지 않는 정확 스캔 변형은 없습니다.** 100,000장면에서 500 ms 아래로 가려면 모든 벡터를 스캔하지 않아야 합니다(ANN).
- 초기 측정에서 variant B가 `equal=false`를 보고한 것은 실험 스크립트가 점수를 `Float32Array`에 담아 순서에 필요한 자릿수를 잃었기 때문입니다. `Float64Array`로 고친 뒤 `equal=true`입니다.
- E는 `searchScenes`의 동점 처리(같은 장면의 두 모달리티가 같은 점수일 때)를 아직 맞추지 않았으므로 채택하지 않았습니다. `scripts/bench-search.ts`에 측정용으로 남겨 두고, 기준이 바뀌면 그때 가드를 붙여 승격합니다.
- ANN 도입 트리거(정확 스캔 p95 `500 ms`)는 100,000장면에서 넘고, 현재 라이브러리(17,439장면, 호스트 p95 417 ms)에서는 넘지 않습니다. FAISS 인덱스는 세대·백필·GC를 소유하는 PR 14에서 실제 규모와 함께 결정합니다.

- quick hash는 파일 크기와 무관하게 정확히 3 MiB(앞·중간·끝 1 MiB씩)만 읽습니다. 그래서 위 표의 quick 처리량은 "샘플 3 MiB를 1.4 ms에 읽었다"는 뜻이고, 실제 읽기 속도로 환산하면 약 2.2 GiB/s입니다. 2 MiB 행은 `quickCoversWhole`이 참이라 quick hash가 곧 full hash입니다.
- full hash는 1 MiB 청크 스트리밍 SHA-256으로 2.7–2.8 GiB/s에 포화됩니다. 64 MiB와 512 MiB가 같은 값이므로 이 수치는 크기가 아니라 SHA-256 연산이 한계입니다.
- 페이지 캐시가 더워진 상태의 측정입니다. 즉 이 표는 디스크가 아니라 CPU 상한입니다. Win11 호스트의 DrvFS(9P)에서는 §3.1의 이미지 헤더 프로브처럼 파일 열기 지연이 지배하므로 실효 처리량은 이보다 낮습니다.
- 실질적인 결론은 처리량이 아니라 읽는 양입니다. 같은 크기를 공유하는 후보라도 quick hash 버킷에 혼자 남으면 3 MiB만 읽고 끝나고, 재스캔은 `stat`만으로 지문을 재사용합니다(해시 0회).
