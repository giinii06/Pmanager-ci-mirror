# 스캔 및 런타임 성능 벤치마크 보고서

모든 수치는 추정치가 아닌 실측 결과입니다. 로컬 합성 측정은 `scripts/bench-scan.ts`를 사용했고, 실서버 측정은 Win11 호스트(`192.168.0.27`, WSL2 Ubuntu 24.04)의 Docker 컨테이너 내부에서 실행했습니다.

## 1. 병목 원인 및 최적화 내용

1. **워처 파일 전수 `stat` 폴링 제거 (`apps/worker/src/watch.ts`)**: 기존 `chokidar`가 `/media` 전체(추가된 `C:\`, `D:\`, `E:\` 마운트 및 `WATCH_POLLING=1` 13,080개 파일)를 수 초마다 전수 `stat()`해 유휴 상태에서도 CPU 63–98%, RSS 713.7 MiB를 점유하던 문제를 등록 라이브러리 한정 디렉터리 `mtime` 폴러로 대체했습니다.
2. **단일 패스 `Dirent` 재사용 (`scan.ts`, `packages/media/src/archive.ts`)**: 디렉터리 내 중복 `readdir`를 제거하고 이미 읽은 `Dirent[]`를 아카이브 탐색에 재사용했습니다.
3. **사전 1회 인덱스 로드 + `O(1)` 맵 갱신 + 250건 WAL 배치**: `preloadLibraryScanIndex`로 기존 에셋 맵을 1회 적재하고, `flushBatch`에서 `PRAGMA synchronous = FULL` 상태로 250건씩 일괄 커밋했습니다.
4. **제한된 비동기 `stat`/프로브 풀**: `STAT_CONCURRENCY = 16`, `IMAGE_PROBE_CONCURRENCY = 8`, `VIDEO_PROBE_CONCURRENCY = 4`로 DrvFS(9P) I/O 지연을 병렬화했습니다.

## 3. 실서버 Win11 WSL2 DrvFS 실측 (`192.168.0.27`)

### 3.1 `D:\` 드라이브 1,000개 합성 파일 벤치마크 (`--dir=/media/drives/d`)

- 디렉터리 열거 (`enumMs`): `111 ms`
- SQLite 쓰기 1,000건 (`synchronous = FULL`, `/data` ext4 볼륨):
  - 단건 커밋 (`1/tx`): `2,700 ms`
  - 배치 커밋 (`250/tx`): **`35 ms`** (77.1배 단축)
- `stat()` 동시성 매트릭스 (`1 -> 4 -> 8 -> 16 -> 32`): **`2,390 ms -> 213 ms -> 155 ms -> 137 ms -> 141 ms`** (동시성 16에서 17.4배 단축)
- 이미지 헤더 프로브 매트릭스 (`1 -> 4 -> 8 -> 16 -> 32`): **`77,143 ms -> 7,754 ms -> 5,525 ms -> 5,503 ms -> 5,529 ms`** (동시성 8에서 14.0배 단축)
- 전체 스캔 합계: 초기 **`9,064 ms`** (`9.06 ms/file`), 증분 **`1,569 ms`** (`1.57 ms/file`), RSS `110.5 MiB`

### 3.2 실제 라이브러리 13,080개 스캔 (`/mnt/e/d`, DrvFS)

- 전체 증분 스캔 (`scan.summary`): `files: 13080`, `unchanged: 13080`, `removed: 0`, 소요 시간 **`3,432 ms`** (잡 완료 기준 `3,472 ms`, 파일당 `0.26 ms`).
- 크래시 체크포인트 재개 + 전체 검증(`Stage 1` + `Stage 2` 전수 순회): `18,900 ms` (잡 완료 `16,431 ms`, 0건 손실).

### 3.3 워커 상시 자원 사용량 개선 (`docker stats`)

## 4. Rust 사이드카 미도입 결정 근거

Win11 `D:\` DrvFS 실측에서 1,000개 `stat(16)`은 `137 ms`, `enum`은 `111 ms`인 반면 9P 파일 열기 기반 프로브가 `5,525 ms`를 차지했고, 13,080개 실제 라이브러리 증분 스캔이 Bun + TypeScript만으로 `3.43초`에 완료되었습니다. 병목은 Bun CPU나 GC가 아니라 DrvFS 9P 파일 열기 레이턴시이므로 별도 Rust 바이너리를 도입하지 않고 단일 TS 런타임을 유지했습니다.

## 5. 뷰어 탐색 쿼리 (PR 07, 12,851개 실측)

`scripts/bench-navigation.ts`로 라이브 DB의 `VACUUM INTO` 복제본(스키마 v20, 활성 자산 `12,851`개)에서 측정했습니다. 수치는 SQL 실행 시간이며 HTTP 직렬화와 `toAssetDTO` 변환은 제외합니다. `getAssetNeighbor`는 `GET /api/assets`와 같은 필터·정렬 SQL을 `ROW_NUMBER()` CTE에서 재사용하고, `pickRandomAsset`은 후보 집합의 `COUNT(*)` 뒤 균등 오프셋으로 한 건을 고릅니다.

| 필터 / 정렬 | 후보 수 | p50 | p95 |
| --- | ---: | ---: | ---: |
| 동영상 / latest | 198 | 0.26 ms | 1.01 ms |
| 동영상 / rate | 198 | 0.36 ms | 0.47 ms |
| 이미지 / latest | 12,653 | 3.77 ms | 4.42 ms |
| 이미지 / views | 12,653 | 9.33 ms | 11.83 ms |
| 이미지 / rate | 12,653 | 11.98 ms | **12.84 ms** |
| 전체 / latest | 12,851 | 4.48 ms | 4.68 ms |
| 전체 / rate | 12,851 | 11.74 ms | 12.27 ms |

| 랜덤 추출 | p50 | p95 |
| --- | ---: | ---: |
| 동영상 (198) | 0.19 ms | 0.23 ms |
| 이미지 (12,653) | 3.25 ms | 3.49 ms |
| 전체 (12,851) | 1.59 ms | 2.72 ms |

- 최악값은 이미지 12,653개를 `rate`로 정렬한 경우의 p95 `12.84 ms`입니다. PR 07 예산(12.8k에서 p95 100 ms 이하)을 충족합니다.
- `rate` 정렬은 평가 버킷 CASE + 평균 시청시간 + 시청시간 + 조회수 + seeded tie-break + `taken_at` + `id`를 모두 계산하므로 다른 정렬보다 약 3배 느립니다. 전체 정렬이 비용의 대부분입니다.
- 200k 규모는 측정하지 않았습니다. 같은 알고리즘이라면 정렬 비용이 약 15배로 늘어 p95 `190 ms` 근처가 될 것으로 추정하며, 그때는 keyset/seek 또는 정렬 스냅샷 도입 여부를 별도 벤치마크로 판단해야 합니다. 이 추정은 실측이 아닙니다.
