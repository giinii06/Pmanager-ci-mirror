## Key Engineering Decisions
1. **Preserve `/media/extra` Mounts:** Live library `npgghj7vxgn4` already stores `root_path = "extra/d"` mapped from `/mnt/e`. Add explicit per-drive `/media/drives/{c,d,e}` mounts as parallel namespaces rather than replacing `/media/extra`, enforce library boundary exclusion when scanning parents, and preserve canonical `libraryId + rootPath` identity.
2. **No Forced Rust Rewrite Before Measurement:** Current `scan.ts` bottleneck is O(N) sequential `stat()` + O(N) per-file `SELECT` + double `readdir()` + unbatched writes. Measure ChatGPT's benchmark matrix across ext4 and DrvFS (`concurrency 1,4,8,16,32`) first; adopt Rust only if Bun CPU/GC dominates over DrvFS/probing.
3. **Host Service Execution Model (Verified Native Docker Engine):** Win11 runs WSL `3.0.5.0` with native `docker.service` enabled inside WSL2 `systemd` (no Docker Desktop volume migration required). Provide one clean boot supervision script/service under the WSL owner identity plus health watchdog.
4. **Windows vs WSL2 SSH:** Enable `ssh.service` inside WSL2 with `authorized_keys` for existing port `22 -> 2222` portproxy, AND provide optional elevated installer support for native Windows `OpenSSH.Server` on an explicit non-conflicting port (`2200`) plus standard Windows OpenSSH documentation.

## Spec v1.0 Program Decisions (2026-11-19)

1. **Sequential PR gate.** PR 00, 01, 02, and 03 land in order before any destructive feature is enabled in production. Each PR commits only after typecheck, the full Bun test suite, the web build, and its own safety checks pass.
2. **Migration numbering follows I-01 with one documented shift.** PR 02 ships `v16` (`library_health` plus the `scan_runs` extensions) and PR 03 ships `v17` (`file_mutations`, `mutation_events`). This is the shift described in decision 9; the original plan to put both in `v16` was superseded when PR 02 needed persisted health on its own.
3. **Fixtures only.** All delete, move, quarantine, and migration tests use temporary directories and cloned SQLite files. No test opens the production host DB for writing.
4. **Feature flags start off.** `FILE_MUTATION_ENGINE_ENABLED`, `HLS_GENERATIONS_ENABLED`, `PLAY_EVENTS_ENABLED`, `SERVER_RANDOM_ENABLED`, `SMART_ALBUMS_ENABLED`, `BULK_OPERATIONS_ENABLED`, `SEARCH_FTS_ENABLED`, `SEARCH_FAISS_ENABLED`, and `NOTIFICATIONS_ENABLED` are off by default. Safety preflight and scanner guards are always on.
5. **Compose has no sample fallback in production.** `compose.yaml` requires explicit drive roots and uses `create_host_path: false`. Sample media moves to a dev override.
6. **Backup before migration.** Every schema PR runs its migration on a cloned DB, compares asset, folder, tag, vote, and playback counts, and only then may the host be upgraded with a fresh pre-migration backup.
7. **Compose split.** `compose.yaml` owns only the required `/media` bind. `compose.drives.yaml` owns the optional extra root and the C, D, and E drives, and requires every path. `compose.dev.yaml` is the only place with `./sample-media`. This keeps a single-drive install working without weakening the full host.
8. **Preflight runs in the container view.** The Windows supervisor runs `docker compose run --rm --no-deps --build api bun run scripts/preflight.ts --require-all`. Checking inside the api container verifies the actual bind mounts, not only the host paths.
9. **Migration numbering shifted by one.** PR 02 ships `v16` with `library_health` and the `scan_runs` extensions because B-03 needs persisted health across restarts. PR 03 ships `v17` with `file_mutations` and `mutation_events`. The spec allows migration numbers to follow the development branch order as long as each migration's meaning and order are documented; `docs/IMPLEMENTATION-BASELINE.md` and this file record the shift.
10. **The Windows supervisor runs a staged copy, not the repo scripts.** `MediaVault-Supervisor` executes `C:\ProgramData\MediaVault\bin\service-runner.ps1`, copied there by an elevated `install-service.ps1`. Editing `scripts/windows/` in the repo has no effect until that elevated install runs again. On 2026-11-19 the staged copy still lacked `compose.drives.yaml`, so a supervisor-triggered `up` recreated `api` and `worker` without `/media/extra` and took the library `OFFLINE` for about two minutes (the scanner blocked and deleted nothing). Treat "ship the Windows scripts" as two steps: commit the repo files, then re-run the elevated installer on the host.
11. **The delete owns its tombstone through `assets.pending_delete_mutation_id`.** A soft delete alone is not enough: the scanner's `touchAssets` and `updateAssetFile` clear `deleted_at` when they still see the file, so an in-flight delete would be resurrected between the quarantine rename and the DB commit. The marker is set by a lease-fenced compare-and-set, both scanner writes refuse a marked row, and `commitPermanentDelete` refuses a mismatched owner. PR 02's scanner guard and PR 03's marker are complementary: the guard stops a mass delete on a bad mount, the marker stops a single delete from being undone.
12. **SIGKILL tests kill at durable boundaries, not inside a transition.** Bun's `db.transaction()` commits natively, so a kill during a transition rolls the whole step back and proves nothing about recovery. The spawned fixture therefore kills between steps (`validated`, `quarantined`, `db_committed`) and, for the final unlink, on the pre-check of the `completed` transition, when the file is already gone and nothing is pending. The narrower "renamed but not yet recorded" window stays covered by an in-process test that constructs that exact state.
13. **An HLS attempt publishes by rename into a unique directory, and the database decides the winner.** Two workers can encode the same generation, so a shared output directory would let a loser overwrite the winner's segments after publication. Each attempt writes into `.tmp-<generation>-<attempt>`, validates, fsyncs, and renames to `<generation>-<attempt>`; the row stores that exact `storage_rel`. `publishHlsGeneration` then re-checks the live job lease, the asset version, delete ownership, and `request_seq`, and only that transaction can make a generation visible. A refused worker deletes its own directory and nothing else.
14. **A file version change clears `hls_active` with a trigger, not application code.** Every path that bumps `assets.file_version` would otherwise have to remember to drop the pointer, and a missed one would keep an old generation's directory alive forever (GC never removes an active row). `trg_assets_version_clears_hls_active` runs after any `file_version` update, so the invalidation is a property of the schema. The API still filters by version, which makes a missed trigger a wasted directory rather than a wrong playlist.
15. **Migration numbering shifted again: PR 04 owns `v18`, so Auth starts at `v19`.** The spec's I-01 numbering assumed Auth would take `v18`; PR 04 needed the HLS tables first because the player and the worker had to change together. The same rule as decision 9 applies: each migration keeps its meaning and order, and the shift is recorded here and in `docs/IMPLEMENTATION-BASELINE.md`. PR 06 Playback and later PRs move up by one accordingly.
16. **Legacy HMAC cookies are rejected at deploy, not carried for 30 days.** A session that cannot be revoked individually is not a session. The transition option (accept old tokens until a persisted sunset) was rejected because it would keep an unrevocable credential alive while advertising `logout-all`, and because this is a single-operator install where one re-login is cheap. The risk that the operator has forgotten the password is covered by `scripts/reset-password.ts`, which was exercised on a scratch database before the deploy. Automated checks mint a real session row with `scripts/mint-session.ts`.
17. **Admission is reserved before the password hash runs.** Counting failures after verification lets a concurrent burst all pass the same limit check and multiply the KDF cost. `admitLogin` counts and inserts a `pending` row in one immediate transaction, the route then verifies, and the row is finished as `success` or `failure`. A two-slot semaphore bounds the CPU even when the limits allow the request.
18. **Legacy scrypt verification uses the exact documented profile.** The old verifier accepted any finite `N/r/p`, so a corrupted row could request gigabytes or throw. The live database was inspected first: both accounts use `N=16384, r=8, p=1, salt=16, key=64`. Only that profile verifies; anything else is a failed login. A successful legacy login rewrites the row with Argon2id under a `WHERE password_hash = ?` CAS.
19. **The edge proxy must forward the port in `Host`.** The origin check compares the full origin, and nginx's `$host` drops `:8080`, so every state-changing request from a browser was refused with `403` until `/api/` used `proxy_set_header Host $http_host`. Verified live: a LAN origin now reaches the login route, while a foreign origin and a portless origin still get `403`.
20. **A play event is identified by a client id and ordered by a per-session sequence.** A retried `POST` cannot be deduplicated on content alone: two real 10-second watches look identical. The client therefore generates an `eventId` once per event and the server stores it as the primary key, so a retry returns the committed result instead of adding a second view or another 10 seconds. Ordering is a separate concern — `seq` must be exactly `last_seq + 1`, and a gap returns `409 sequence_gap` with `expectedSeq` so the client can renumber rather than silently skipping. The alternative (dedupe by `(session, type, client_timestamp)`) was rejected because two distinct events can share a millisecond and a clock change would break it.
21. **Session creation is itself retryable, and a view is recorded once by a conditional update.** A lost `201` would otherwise leave the client unable to send events without creating a second session. `client_session_key` plus `UNIQUE(user_id, client_session_key)` makes the create idempotent and returns the existing session on retry. The view counter moves only when `UPDATE ... SET view_recorded_at = ? WHERE id = ? AND view_recorded_at IS NULL` changed a row, so a duplicate view event cannot double-count even if its id differs.
22. **The legacy progress write is fenced, not removed.** `PUT /api/playback/:id` still answers `204` for an older tab, but only while `last_session_id IS NULL`; once a session owns the row, a stale tab cannot overwrite the position or the version. Removing the route would break a page that is still open during the deploy; leaving it unfenced would let the old path fight the new one. The fence is the smallest change that makes the two writers mutually exclusive, and the route is documented as legacy.
23. **Resume is a state machine, not a fetch-then-seek.** The saved position arrives asynchronously and can land after the user has already seeked. `ResumePosition` therefore has one offer path with a fixed priority (explicit `startMs`, then a seek in this session, then the saved record), marks itself `applied` before moving the playhead, ignores offers of `5s` or less, and treats `duration - 8s` as finished. Without that ordering a slow response visibly yanks the playhead backwards, which is the exact race C-05 names.
24. **A vote carries a client request id so a double click is one vote.** The vote counter is a denormalized column, so the old `UPDATE ... votes = votes + 1` could not tell a retry from a second click. The deterministic `vote_events.id` (`client:asset:<actor>:<assetId>:<reqId>`) makes the event insert the arbiter: the counter only moves when the insert was new. The UI also disables the button while the request is in flight, but the server rule is what makes it correct.
25. **Neighbour navigation reuses the list's own order SQL through a window rank.** `getAssetNeighbor` builds `filtered` with `buildWhere`, computes `ROW_NUMBER() OVER (ORDER BY buildOrderExpression(...))`, and selects rank `anchor.rn ± 1`. A per-sort keyset predicate would be faster in principle, but `rate` combines a rated CASE bucket, an average-watch division, a seeded pseudo-random tie-break and `taken_at`/`id`, and re-implementing that comparison by hand would drift from the grid. The window version cannot disagree with `GET /api/assets` because it is the same SQL. Measured on the live clone (12,851 assets): worst p95 `12.84 ms` (`rate` over 12,653 images), well under the 100 ms budget. A keyset/hybrid path is deferred until a 200k benchmark shows the window cost exceeding it. ChatGPT (`mediavault-pr07-navigation-01`) recommended the same option and flagged the 200k cost; that flag is recorded as a benchmark follow-up, not a blocker.
26. **Random navigation samples the eligible set instead of retrying draws.** The first draft drew up to three times and skipped a hit on the current/recent assets; with a 2-asset pool that fails 12.5% of the time, and with 4 of 5 recent it fails 51%. `pickRandomAsset` instead counts the filter's membership minus the current asset and the recent list, draws one uniform offset, and only relaxes the recent list when the strict set is empty. The current asset is never returned. `crypto.getRandomValues` with rejection sampling keeps the offset uniform; a caller-supplied `seed` makes tests deterministic. Random deliberately does not use `buildOrder`: shuffle only needs uniform membership, so ordering by `id` avoids the expensive `rate` sort. This follows the consultation's recommendation and replaces the retry design.
27. **Viewer navigation is guarded by a session and a request generation, not by abort alone.** `open`/`close` bump `sessionId`, and every explicit navigation (`next`, `prev`, `select`, `removeAsset`, and each server request) bumps `navigationRequestId`. A response applies only when both still match, so a slow neighbour or random response cannot overwrite a newer selection, resurrect a closed viewer, or clear `loadingNext` for a different request. `AbortController` cancels the network work but is not treated as the correctness mechanism, because an already-settled promise can still run. Repeated next/prev while a request is in flight is ignored rather than queued, which keeps the navigation order deterministic.
28. **A viewer opened without a filter has no server scope.** `open([asset], 0)` (a shared video link) no longer implies the whole library: the store leaves `filter` null and next/prev/shuffle stay local. The shared-link call site in `VideosPage` now passes an explicit `{kind:'video', sort, seed}` filter, so the intended behaviour is stated where the context is known. The search-hit viewer keeps its single-asset scope. This implements the consultation's warning against silently broadening a single item to the library.
29. **A waiting GPU job's ETA is the holder's remainder plus its own median, and the median already contains model load.** `workQueue` finds the one running row that owns the card and computes its remaining time from the lane median; every `waitingGpu` row then reports `holderRemaining + ownMedian` without subtracting its own wait, because a job that has not taken the card has not started. A separate model-load constant was rejected: each Python stage loads its model *after* acquiring the lease, so the median measured from claim to completion already includes that load, and adding a constant would double-count it. Lane ETAs still measure only the lane's own GPU work, so summing the four GPU lanes stays the true serial total instead of counting the holder's remainder once per lane.
30. **Scene coverage is computed from the same plan the worker executes.** `sceneWindowCount` mirrors `plan_windows` in `apps/scene-worker/src/scene_worker/stage.py`; the API receives `SCENE_MAX_WINDOWS` (default 120) so the panel's "N/M 구간" matches the job instead of assuming full coverage. This satisfies D-01's sampling display without a schema change. Persisting coverage for *completed* indexes (D-04's "저장") belongs to the checkpoint/index-metadata slice, because it needs a row that outlives the queue entry.
31. **Environment failures park, and recovery requeues only what it can prove is healthy.** `failJob` treats `SOURCE_OFFLINE` and `DISK_FULL` as terminal without consuming the retry budget, because retrying an unplugged drive only hides the cause. `requeueSourceOfflineJobs` requires the library's health row to be `ONLINE` (or no library at all), resets `attempts`, and re-checks the active-key guard inside the `UPDATE` so a paused row with the same dedupe key cannot turn a requeue into a constraint error. Legacy failures without a `[CODE]` prefix are untouched, so the deploy requeued `0` rows on the live clone.
32. **The common `stage_checkpoint` table moves to its own schema slice.** D-04's protocol (write a unit, fsync the artifact, write a manifest, then a DB checkpoint, and reconcile the two on restart) spans all four AI workers and needs artifact storage that outlives a job row. PR 08's acceptance is lease/progress/recovery accuracy, and the spec already assigns `v21`–`v25` to PRs 10–14; a table with no resume path would be dead weight, and a rushed resume path risks marking a partial index complete. The table therefore lands as `v21` before PR 10, shifting Duplicates to `v22` and the later PRs by one under the rule of decisions 9 and 15. Trigger: before a full-library scene/ASR backfill, or as soon as a stage routinely approaches the lease window.
33. **The Node encoder runs in its own process group, so a cancel takes its helpers down.** `Bun.spawn(..., { detached: true })` calls `setsid()`, which makes ffmpeg the leader of a new group; the timeout and abort paths call `process.kill(-pid, 'SIGKILL')` and fall back to `proc.kill(9)` if the group is already gone. A fixture that spawns a helper proves the helper dies with the encoder. This is the Node half of D-05; the Python half uses `run_checked`/`terminate_group` with TERM → 10s → KILL.
34. **The window log is the source of truth; the manifest names it and the DB row points at the manifest.** D-04's ordering is write the unit → fsync the artifact → temp manifest → rename → DB checkpoint. A crash can therefore leave the log ahead of the manifest, or the manifest ahead of the DB. On load the stage replays the log, stops at the first torn line, seq gap, missing thumbnail or planned total, truncates the torn tail with fsync, and rewrites a lagging manifest; a manifest whose meta does not match the current plan discards the log instead of attributing old vectors to a new model or window plan. The DB row is only a hint for the claim, so a lost row costs the next claim its ETA hint, never correctness.
35. **The stage re-derives the prefix from disk and ignores the claim's checkpoint.** A claim can move to another worker, and the row can lag the log by up to four windows. Trusting the row would either skip windows that are not on this volume or re-encode ones that are. The claim field is still returned because the API needs a place to report that a prefix exists, and a future stage can validate the manifest hash against it; the current stage only uses its own `meta` comparison. The meta covers asset, file version, model SHA, pipeline version, dimensions, duration and the window plan, which is exactly what determines the vectors.
36. **The manifest is written every five windows, so a crash loses at most four finished windows.** Every window already pays one fsync for its log line and one for its thumbnail; rewriting the manifest on every unit would add two more fsyncs plus a rename per window for no correctness gain, only a smaller replay. Five bounds the replay to four windows (a few minutes on the GPU) while keeping the durable-write cost linear in windows. Completion always writes the manifest, so a job that finished all windows never replays anything and skips the model load entirely.
37. **The checkpoint row outlives a failed job but not a completed one.** Completion deletes the row and the worker removes the directory after the API accepts the scenes, because the windows are now in `video_scenes`. A job that exhausts its attempts keeps its row and log, so a manual re-index of the same job id resumes from the prefix instead of recomputing it; that is also why `failSceneJob` does not clear them. A changed model or window plan is handled at claim time (the row is dropped) and at load time (the log is dropped), so a stale prefix cannot leak into a new index.
38. **FTS5 trigram is a candidate generator; LIKE remains the answer.** A trigram token needs three code points, and most Korean words are two (`바다`, `그래`, `생각`), so an engine that replaced LIKE would break the most common query shape. Every statement therefore keeps the LIKE predicate and adds `MATCH` only to shrink the rows it re-checks. `ftsPhrase` quotes the term and refuses control characters or fewer than three code points, and a query that cannot produce a phrase never touches the index. This reads the spec's "FTS5 fallback" backwards on purpose: FTS is the optional accelerator, LIKE is the contract.
39. **Readiness is an integrity proof, not a row count.** `count(*)` on an external-content FTS table reads the content table, so it says nothing about the index itself; a stale but non-empty index would pass any count gate and silently return short results. Startup runs `INSERT INTO <tbl>(<tbl>, rank) VALUES ('integrity-check', 1)` — `rank` is load-bearing, because the plain form performs the weaker check that ignores a missing index — rebuilds once on failure, re-checks, and otherwise disables the fast path for that process. `%_docsize` supplies the document count for the log line.
40. **The candidate ceiling is per corpus, from the measured per-row cost.** Filenames cost about `0.03 ms` per 10k LIKE rows, so more than `limit * 8` candidates loses to the scan. Dialogue pays two joins and a correlated subquery per segment (about `1.4 ms` per 10k), so `limit * 64` still wins: `3.41 ms` against `15.45 ms` at 100k segments. The count itself is bounded (`SELECT count(*) FROM (… LIMIT cap)`), so a common term costs a short FTS scan rather than a full join. The constant will need re-measuring if the transcript count grows by an order of magnitude.
41. **The search index writes rows the content table did not write, so mutations report on `RETURNING`.** `sqlite3_changes()` counts trigger-written shadow rows: `DELETE FROM assets` reported two changes for one asset, and `updateAssetFile` reported more than one. Both now select `RETURNING id` and treat a returned row as success, with a test pinning it. Without the change every scanner rename and every permanent delete would have reported failure.
42. **The exact scene scan stays; ANN is deferred to PR 14 with a measured trigger.** At 17,439 scenes / 52,317 embeddings the scan is `147.51 / 158.34 ms` p50/p95 on the Mac clone and `373.19 / 417.41 ms` on the host, where the same LIKE scan is also 1.6-8x slower; at 100,000 scenes the clone measures `827.63 / 995.25 ms`. Two exact-scan rewrites were measured and neither is a reliable win: variant A ranged from 9% faster to 7% slower across two runs, and variant B changed the tie order. The spec's 500 ms ANN trigger is crossed only at 100k scenes, 5.7x the current library, and FAISS needs the generation/backfill/GC machinery that PR 14 owns. Recorded rather than dropped.
43. **The duplicate feature is review-only, and the schema says so.** The acceptance is "정확 중복 오탐/자동 삭제 0", so `duplicate_groups.state` allows only `open`, `ignored` and `kept`; there is no value that records "deleted", and no code path can add one without a migration. `POST /api/duplicates/groups/:id/decisions` refuses `action: "delete"` with `409 delete_not_available`, and the scan opens no file for writing. A test asserts that a scan leaves `file_mutations`, `mutation_events` and `jobs` empty and no `pending_delete_mutation_id` set.
44. **A group id is derived from its content, so a reviewer's decision survives a rescan.** `duplicateGroupId` is `dup_` + the first 16 hex of `sha256('exact:' + fingerprint)`, and `replaceDuplicateGroups` upserts with `ON CONFLICT(id) DO UPDATE SET updated_at = excluded.updated_at` only. A random id would orphan the `kept`/`ignored` decision on every scan. The list orders by `created_at` rather than `updated_at` for the same reason: a rebuild touches every row, and a cursor page must not reshuffle underneath a reader. The kind is a parameter of the call rather than a field of each group, so "the exact set is now empty" is expressible (an empty array still clears the kind) and an input mixing two kinds cannot be built.
45. **The fingerprint carries the size as well as the hash.** `exactFingerprint(sizeBytes, fullHash)` produces `sha256:<bytes>:<hex>`. The grouping key the spec names is `(size_bytes, full_hash)`, and folding both into the identity makes the two impossible to merge even if two different sizes ever produced one hash, which `ux_duplicate_groups_fingerprint` would otherwise allow silently.
46. **`device_id`, `inode` and `same_inode` are additions beyond the spec's column list.** Two hardlinks are one body of bytes on disk reached by two paths: a true duplicate by content, but deleting either destroys both. Without these columns the API cannot tell a hardlink pair from two real copies, and the spec explicitly requires special handling. A member whose inode or device is unknown is never treated as a link, because two unreadable files would otherwise look linked.
47. **Reuse is keyed on the stored quick hash, not the full hash.** The brief's condition was "a non-null `full_hash`", but a candidate alone in its quick-hash bucket stores only a quick hash, so that rule would re-read 3 MiB for every non-duplicate on every scan. The scanner bumps `file_version` on any change, so a stored row for the current version describes the current bytes, and the reuse fence is the stat signature (size, mtime, inode, device) — exactly as strong for a quick hash as for a full one. Measured: a rescan of two duplicates reports `hashed 0, reused 2`.
48. **A small file's quick hash is its full hash, so it is read once.** `quickCoversWhole(size)` is `size <= 3 MiB`; the quick read is then the whole file and `quickHash` returns the full digest with `whole: true`. This removes the second read for the most common duplicates (thumbnails, short clips) and makes the `whole` flag a property of the size, so a stored row can be classified without re-reading it.
49. **The duplicate scan is a `maintenance` job in the existing `jobs` table and the existing nine-lane contract.** No new table, no new lane, no new config. `LANE_STATES.maintenance` maps `running`/`failed` so the state is reported correctly. Known gap, recorded rather than hidden: the `media` lane query selects every `jobs` row, so a maintenance job is still listed under `media` until the queue page (stage B) gives the lane its own query.
50. **The scan refuses a path that leaves its library root through a symlink.** `resolveInside` is string arithmetic and cannot see a link. The scan resolves both the library root and the file with `realpath` and refuses the candidate when the real path is outside the real root, counting it as `refused` rather than `missing`. A disconnected drive therefore fails the candidate, not the job.
51. **`kind=similar` returns empty without touching the database.** Perceptual hashing is a documented follow-up. An empty answer is honest; a guessed one would put unverified pairs in front of a reviewer under an acceptance that says "no false positives".
52. **No feature flag.** The scan only reads bytes and writes its own two tables. There is nothing to disable, because a wrong answer is a review item rather than a file change. This differs from the delete, HLS and search flags, which all gate a behaviour that can change what a user sees or loses.
53. **The exact set is rebuilt globally, not per requested library.** A pair can span two libraries and `file_fingerprints` has no library column, so a per-library rebuild would delete another library's groups. `duplicateCandidates` is scoped by `libraryId` (the expensive part is reading bytes), while `exactDuplicateGroups` reads every live fingerprint (cheap, and the only correct scope).
54. **The `media` lane stops claiming every `jobs` row; maintenance gets its own query.** Decision 49 recorded the gap: `media` was `SELECT … FROM jobs`, so a duplicate scan appeared as a media job and the lane's counters counted it twice. `media` and `mediaCounts` now exclude `kind = 'maintenance'`, and a separate `maintenance` query/count feeds the ninth lane from the same table. The alternative — moving scans to a dedicated table — would have meant a second queue contract for one job kind. A test inserts one media job and one maintenance job and asserts each lane sees exactly one, so the split cannot regress silently.
55. **The page reports reclaimable bytes as the group total minus its largest member.** That is the space a reviewer could free by keeping one copy, and it is deliberately not attributed to any particular member: the UI has no delete action, so naming a "loser" would imply a choice the feature cannot make. Hardlink members are marked with a link badge and the group's reclaimable figure is still shown, because a hardlink pair frees nothing when one path is removed — the badge is the warning, and the number stays an upper bound rather than a promise.
56. **A saved filter is a bounded `FilterNode` tree, validated once and compiled once.** The spec names `and/or/not` over `field/operator/value`, and a flat query cannot say "not tagged X and no transcript" without ad-hoc flags that multiply. `packages/shared/src/filters.ts` declares the 20 fields, their operators, value shapes and limits (depth 5, 50 nodes, 100-element lists, 200-character text) and owns `parseFilterTree`; `packages/database/src/filter.ts` compiles the parsed tree into one parenthesized predicate over `assets a`, binding every value and taking column names only from its maps. `AssetFilter.where` carries the compiled object, so the page, the count, `listMatchingAssetIds`, `getAssetNeighbor` and `pickRandomAsset` all read the same predicate instead of rebuilding it.
57. **The API validates a filter with `parseFilterTree`, not a second Zod mirror.** A Zod mirror of 20 fields times their operators is a second validator that drifts from the compiler; the envelope in `apps/api/src/filters.ts` returns the parser's path (`filter.root.children[0].value[1] …`) as a `400 invalid_request`, so the client sees the same detail a Zod issue would carry. This is a deliberate reading of the spec's "Zod 검증": the request body is validated server-side before storage, by the one function the read path also uses. Other request bodies keep Zod.
58. **A stored album filter fails closed.** `smart_albums.filter_json` is re-parsed on every read; a tree that no longer parses or compiles makes the album's asset routes answer `409 album_filter_invalid` (and the DTO carries `filter: {valid:false, error}` so the UI can offer a repair). Falling back to "match everything" would show the whole library under the album's name, which is the one failure mode a saved filter must not have.
59. **`rate` has one definition, and a rate predicate ranks the global rated set.** `RATE_RANKED_SQL` is the body `computeAssetRates` uses for the number the gallery displays, and the compiler wraps the same body in `a.id IN (WITH … SELECT id FROM ranked WHERE rate …)`. Ranking only the filtered subset would change every percentile the moment a filter is added, so the filter and the displayed rate would disagree.
60. **The smart-albums flag defaults on, with `SMART_ALBUMS_ENABLED=0` as the kill switch.** Spec I-05 says new flags start off; this deviates for the same reason PR 09's FTS flag did: the feature only reads existing rows and stores validated JSON, the tests cover the invalid and unauthorized paths, and the operator can turn it off without a deploy. A flag that hides a read-only review feature by default would leave the deployed UI dark with no way to see it except an env edit. Recorded rather than silently kept.
61. **A playlist item is a slot, so the same asset may appear twice.** `playlist_items` has its own `id` and a plain `position`; `(playlist_id, position)` is not unique, and a reorder rewrites every position to its index inside one immediate transaction. A unique position would force temporary offsets during a move, and a `(playlist_id, asset_id)` key would forbid the duplicate a user expects when building a queue.
62. **Watch later is a `kind`, not a magic row id, and creating it is idempotent.** `playlists.kind` is `custom|watch_later` with `ux_playlists_watch_later` on `(user_id) WHERE kind = 'watch_later'`, so "one default list per user" is a database invariant. `createPlaylist` returns the existing watch-later row when it loses the insert race, and `ensureWatchLater` retries `나중에 보기`, `나중에 보기 2`, … because a user may already own a custom list with the default name (that collision hits the name index, not the kind index). SQLite names the violated columns rather than the index, so the two cases are told apart by whether `playlists.name` appears in the error.
63. **A bookmark records the file version it was placed on, and editing never re-anchors it.** A timestamp refers to a moment in a specific encode; after a re-encode the same millisecond may be a different frame. `video_bookmarks.file_version` is captured at creation, `stale` is computed at read time against `assets.file_version` (a stored flag would make every scan rewrite bookmark rows), and `updateBookmark` changes the note or position without touching the version, so the mark stays visibly stale until the user places a new one.
64. **The web editor edits a bounded shape over the general tree.** `FilterBuilder` produces `and([and|or(rules), not(or(none))])`, which covers the spec's AND/OR/NOT cases and every state the UI can show. A stored tree outside that shape still compiles and serves its album, but the editor reports that the conditions are more complex than it can show and offers to overwrite rather than silently dropping branches. The API remains the general contract.
65. **A custom poster publishes all sizes or none, and only for the file version it read.** `extractCustomVideoPoster` stages every size beside its target, runs `canPublish` once, then renames each staged file into place; a refused fence or a failed resize leaves the previous poster untouched instead of replacing 320 and keeping the old 640. The API route's fence re-reads `file_version` (the synchronous capture has no job lease, unlike the worker's thumbnail stage) and `bumpPosterVersion` takes the expected version in its `WHERE`, so a scan that changes the file mid-capture answers `409 file_changed` rather than bumping a poster that no longer describes the file. An unreadable frame answers `422 poster_capture_failed`; both leave `poster_version` unchanged, so the browser's `pv` cache key does not move. The staging makes a refused capture clean, not a multi-file rename atomic: an I/O failure partway through the rename loop, or two captures for the same version racing from different tabs, can still mix sizes. Neither case bumps a version it did not publish, and the UI serializes its own captures with the pending state.
66. **The bulk executor runs in the rw worker beside the mutation loop, not in the API.** The API only resolves the selection, validates params and writes the parent plus its items; the worker claims one operation at a time on a lease, and each item commits its own state. A 10,000-file operation cannot be one HTTP request, and a second executor would need the mutation engine's file ownership, quarantine and lease rules again. File kinds (`delete`, `move`, `copy`) are delegated to `file_mutations` with a deterministic request key `bulk:<operationId>:<itemId>` and the item polls the mutation row; inline kinds (`tag_add`, `tag_remove`, `poster`, `reanalyze`, `export`) run in the bulk loop because they are short database writes. This keeps exactly one process allowed to touch files.
67. **The preview's generation token is a hash of the resolved selection, and create re-resolves it.** `preview` resolves an id list or a filter once, hashes the canonical selection, and returns `base64url({v,kind,count,hash,at})`. `create` resolves the same selection again and refuses with `409 selection_changed` when kind, hash or count differs. Without that check a scan or a new upload between preview and confirm would act on a set the user never approved. A query selection is stored as the filter, not 10,000 ids, so the frozen set is reproducible without a second client payload.
68. **An item snapshots its filename, relative path and size at creation.** The report must still name a file after a delete removed the asset row, and the progress page must not join a row that no longer exists. The live asset is read only for the work itself, so the snapshot is evidence, not a cache to refresh.
69. **A move quarantines the source before the database commit, reversing the spec's stated order.** F-04 says DB change then quarantine. The reverse leaves the file at the old path while the DB already names the new one; a crash in that window lets the next scan index the same bytes twice and the user sees a duplicate. Quarantine first means a crash before the commit leaves the source missing from the old path but present in the hidden quarantine, which the resume path recognizes; a crash after the commit leaves the target published and the quarantine disposable. The hidden `.mediavault-quarantine` directory is skipped by the scanner, so neither order can double-index.
70. **Same-filesystem rename is the default, and EXDEV is the only proof a copy is needed.** Two bind mounts of one disk report the same `st_dev`, so a device comparison would choose rename and fail at runtime. `commitMove` therefore tries `rename(2)` inside the immediate transaction and falls back only when the error code is `EXDEV`. The copy path writes `<target>.<mutationId>.tmp`, fsyncs it, compares SHA-256 on both sides and the size, then renames it into place and quarantines the source. A same-FS rename keeps the inode, which is what proves the target is our file on resume.
71. **A move reuses the `file_mutations` state machine and adds only `target_library_id`/`target_rel`.** Delete's states already encode requested → validated → quarantined → db_committed → purging → completed, and its lease fence, retry and recovery paths are tested. A second state machine for moves would duplicate the crash semantics and split the worker's claim query. The target columns are additive so an existing row's meaning is unchanged, and a move never bumps `file_version`: derived thumbnails, scenes, transcripts, votes, tags and bookmarks stay valid because they are keyed by asset id and version, not path.
72. **A move claims the asset through `pending_delete_mutation_id` without setting `deleted_at`.** The scanner's `touchAssets` and `updateAssetFile` already refuse a row whose pending mutation is set, so a move gets the same protection from a concurrent scan that a delete gets while the asset keeps serving its old path until the commit. Reusing the column avoids a second claim column; `deleted_at` staying null is what keeps the asset visible during the move, and `updateAssetLocation` clears the claim in the same transaction that changes the path.
73. **Cancel stops at the last safe step, and retry is a separate decision.** `POST /cancel` cancels only `pending` items and asks the worker to stop an in-flight item through `cancelMutationPreCommit`, which succeeds only while the mutation is `requested`/`validated` and no worker holds the lease. A quarantined, committed or completed file is never reported as undone; it stays succeeded and the operation finishes as `cancelled` with those items intact. `POST /retry` is allowed only on a terminal operation with no live lease, and only resets `failed`/`held` items whose mutation is gone, so a retry cannot start a second file operation for the same asset.
74. **An export settles its items before writing the CSV.** The export has no per-item work, so writing first recorded every row as `pending` and then marked it succeeded, which made the downloaded file disagree with the page. The rows are now marked succeeded and the file is written from their final state; a failed write is retried by the operation and rewrites the same file.
75. **Reanalysis forces the scene and embedding jobs.** `createSceneJob`/`createEmbeddingJob` return the existing row when the model fingerprint still matches, which is exactly the state a user asking to reanalyze wants to leave. Both take `force` and reset a finished row to `queued`; ASR keeps its own reset rules because a current failure waits out a cooldown. The bulk operation snapshots the model revisions at create time, so a later deploy cannot silently change what the operation produces.
76. **The `bulk` lane reads `bulk_operations`, not its items.** A 10,000-item operation is one queue line with a percentage, because the per-file detail belongs to the bulk page and listing 10,000 rows would bury every other lane. The query counts finished items for the percentage and reports the parent's state, so the queue never invents a state the operation does not have.
77. **The web selection is either a set of ids or the filter, and the action bar never pretends the two are the same.** Tiles toggle ids; "조건 전체" replaces the set with the current filter so the server resolves it once. Switching back to tiles drops the filter. The preview dialog blocks only structural problems (`no_assets`, too large, engine off, target missing/offline, tag missing); warnings such as a soft-deleted target or an offline source are shown but do not block, because those files are held per item and the user can still run the rest. A delete requires typing `delete` in the dialog, and the API independently requires `params.confirm === 'delete'`.
78. **The ChatGPT second opinion for PR 12 was unavailable and the run continued without it.** The `chatgpt-use` session was not open (`session_unavailable`), and the skill's rule is to record the skip rather than retry into the same failure. The contested call was decision 69 (quarantine before DB commit); it is backed by the crash-window argument above and by the resume tests, and it remains the item to revisit if a reviewer finds a counterexample.
79. **A pending claim hides the asset from a scan's missing sweep, not only from its update.** A move keeps `deleted_at` null and renames the source into quarantine before the DB commit, so for a moment the old path is empty while the asset row is still live. `softDeleteMissing`/`countMissingAssets` now skip any row with `pending_delete_mutation_id` set; otherwise a scan finishing inside that window would hide the asset, `updateAssetLocation` would refuse the commit, and the move would retry against a row the scan had just deleted. `touchAssets`/`updateAssetFile` already had the same guard, so this closes the last scanner path that could act on a claimed row.
80. **Cancelling a pre-commit mutation releases the claim it took.** Validation claims the asset: a delete sets `deleted_at` and `pending_delete_mutation_id`, a move sets only the mutation id. Cancel used to write state `cancelled` and leave the claim, so a cancelled delete kept the asset hidden forever and a cancelled move made every later mutation answer `asset_owned_by_other_mutation`. `cancelMutationPreCommit` now clears `pending_delete_mutation_id` and restores `deleted_at = NULL` for a delete in the same statement that moves the row to `cancelled`, guarded by the claim id so a stale cancel cannot free a claim another mutation owns. Both cases are pinned by tests.
81. **A bulk item settles when it can no longer make progress, and an engine that is off must not strand the operation.** The reconcile loop now holds a `failed_retryable` item whose `attempts` reached `maxAttempts` instead of leaving it retryable forever. When `FILE_MUTATION_ENGINE_ENABLED` is off on a restart, the operation moves to `cancelling`, pending file items are cancelled, and in-flight mutations are cancelled only while still pre-commit; an item whose file state is uncertain is held rather than reported undone. Without this a worker restarted with the engine disabled kept claiming the same operation and running the same items.
82. **A resumed move proves the target before it trusts it, and a copy never adopts a stranger's bytes.** A crash after the copy is published and the source quarantined leaves `phase: 'copied'` with a target that may or may not be ours. `targetMatches` compares the recorded SHA-256 when the manifest has one and falls back to the inode for a same-filesystem rename; `commitMove` takes `targetVerified` so the resume path does not publish a second time, and a mismatch blocks with `target_exists` instead of committing. A copy whose target already holds different bytes is refused the same way, so neither path can record an asset over a file it did not write.
83. **The destination directory is resolved again inside the commit transaction.** Validation runs minutes before the rename, and a directory component swapped for a symlink in between would redirect the publish outside the library. `assertTargetDirSafe` re-runs `realpath` and the containment check synchronously inside the immediate transaction (`target_outside_library` / `target_path_invalid`), and the copy's publish step repeats it. This is the one check that has to sit in the transaction rather than at prepare time.
84. **PR 13 is incident-centric, not sample-centric.** Notifications are rows with a stable `dedupe_key`, an `open|resolved|dismissed` state, an occurrence count and a last-notified time; the worker reconciles the current findings against them. A periodic time-series table would add write volume, retention and a second aggregation model for a single-PC server whose existing tables already hold the history. Diagnostics is a live snapshot composed from those tables, not a stored sample.
85. **The notification inbox is system-wide and `NOTIFICATIONS_ENABLED` defaults off.** The server has one operator, so a `user_id` on every notification would duplicate rows and delivery attempts for no benefit; `read_at` still tracks the unread badge. The flag defaults off per spec I-05 because the evaluator writes rows and can deliver to an external webhook. Diagnostics and cache cleanup stay always-on because they only read or delete regenerable orphans.
86. **Diagnostics are available to every authenticated user, with absolute roots redacted.** There is no role column and the host has two equal users; adding a role model for one endpoint would be a larger change than the feature. The report replaces the media, cache, data and AI roots with `<media>`, `<cache>`, `<data>` and `<ai>`, and the endpoint is cookie-authenticated like every other `/api/` route.
87. **The HLS GC candidate query is widened so a superseded generation can be collected even without `eligible_for_gc_at`.** `trg_assets_version_clears_hls_active` deletes the active row when `file_version` changes but never sets the GC timestamp, and the old query required it. A `ready` generation with no `hls_active` row and one hour of idle time is now eligible; the active row still protects the generation in use. This is the cache-policy fix the spec's H-04 implies, not a new GC.
88. **Manual cache cleanup deletes only orphaned or old regenerable entries, and HLS stays with the worker GC.** The clean endpoint removes stale temp, orphaned thumb/preview version directories (asset missing, deleted, or `file_version` mismatch), scene thumbnails for missing assets, and export CSVs past the cutoff. Originals, the DB, quarantine, models, the current version and the active HLS generation are never candidates. HLS cleanup remains the worker's `deleting` state machine, because deleting a directory without moving its generation row would leave the DB describing a file that no longer exists. The preview carries a hash-backed generation token and a changed set answers `409 cache_preview_changed`.
89. **Disk pressure excludes write-heavy kinds from the claim instead of failing them.** The worker reads `statfs` every 30 seconds; below `MIN_FREE_BYTES` or `MIN_FREE_RATIO` it passes `excludeKinds` to `claimNextJob`, so thumbnail/preview/HLS jobs (cache volume) or archive extraction (media volume) stay queued and run when space returns. Failing them would burn retry budget and produce a failure strip for a condition the worker can see coming.
90. **Request IDs are server-minted and a diagnostic ID is added only to 5xx bodies.** Fastify's default counter is per-process and its inbound header is off. `genReqId` mints a `newId(16)`, every response carries `X-Request-Id`, and an `onSend` hook injects `requestId` into all JSON error bodies. A 5xx also gets an 8-character `diagnosticId` logged with the error, because the masked 5xx body otherwise has nothing an operator can search. 4xx bodies keep their stable error code as the diagnostic.
91. **Worker heartbeats use a per-boot instance id.** In Docker the worker id is `worker-1` on every restart, plus `worker-1:mutation` and `worker-1:bulk`, so a table keyed on `worker_id` cannot count restarts. `worker_heartbeats.instance_id` is a random per-boot id, `worker_id` stays the job-fencing identity, and restart-loop detection counts distinct instance ids in the last hour. Rows are pruned after seven days.
92. **`recovery_logs` keeps its startup-only meaning; the heartbeat is a new table.** The periodic recovery pass deliberately records nothing, and repurposing the table would change what `/api/system/status` means by "last recovery". A worker that has been up for weeks should not look like it recovered weeks ago; the heartbeat answers "is it alive now".
93. **Backup failures back off 15 minutes; asynchronous backup creation is deferred.** The worker currently retries a failed backup every 60 seconds because it only looks at the age of the last success. A retry timestamp stops the log and DB churn without changing the 24-hour schedule. `POST /api/backups` still runs `VACUUM INTO` synchronously on the event loop; moving it to the existing `backup` lane is a separate change with its own crash semantics and is recorded in `pending-tasks.md`.
94. **`jobs.request_id` is an additive correlation column.** The API mints the request id, the enqueue sites store it, and the worker logs it on failure so a user-reported diagnostic id can be traced to the job that failed. Worker- and timer-originated jobs leave it null; no existing query changes meaning.
95. **No Prometheus/OTel service; the JSON metrics endpoint is the default.** Spec H-02 asks for structured JSON and a SQLite aggregation API on a single PC, with exporters optional. `GET /api/system/metrics` returns route-pattern p50/p95/max, 4xx/5xx counts, WAL/page stats and queue counts without new infrastructure or id labels. A `compose.monitoring.yaml` exporter can be added later against the same snapshot.
96. **One incident sends at most one Discord alert and one recovery, however long it persists.** `enqueueNotificationDelivery` is unique on `(notification_id, message_kind)`, so the per-kind cooldown governs the in-app `last_notified_at` (and a later re-open after a resolve) rather than a recurring webhook reminder. The design table's cooldowns were written before the delivery table existed; one message per incident matches H-03's "one incident, one notification" and keeps a two-day disk-low condition from paging every hour. A reminder needs a new message kind, not a looser unique index.
97. **The diagnostics report is cached for 30 seconds and only a download is audited.** The report walks the cache tree and stats every volume, and the page polls every 30 seconds; sharing one snapshot per window keeps the poll cheap. `?refresh=1` bypasses it for the manual button. `diagnostics_runs` records downloads only, because a row per poll would be 2,880 audit rows a day for no operator value.
98. **A bulk retry moves the terminal mutation's request key aside instead of reusing it.** A bulk file item's request key is `bulk:<operation>:<item>`, and `createMutation` deliberately maps one key to one row forever. A retry therefore returned the blocked mutation and held the item again without touching the file. `retryBulkItems` now rewrites the attached mutation's key to `<key>:retry:<mutationId>` in the same immediate transaction that resets the item, so the next attempt creates a fresh row under the original key while the old row and its `mutation_events` stay as the audit trail. The rewrite is limited to terminal states (`blocked`, `cancelled_pre_commit`, and `failed_retryable` at `max_attempts`); a live or completed mutation is never displaced. Decision 73's "mutation is gone" condition becomes "the mutation is terminal and its key is moved aside".
99. **The rollout rehearsal runs in a separate compose project, not by turning the live flags on.** The live library has no disposable assets and the delete/bulk flags are process-wide, so a rehearsal on the live stack would expose every real asset to the engine for the duration. A `mv-rehearsal` project with its own named volumes, port, media root and fixture files exercises the same images and env flags while the live project keeps its flags at `0`. The only shared state is the Docker image cache; the live database and media root are never mounted into the rehearsal containers. The rehearsal is then torn down with `down -v` and its images and fixture tree removed.
