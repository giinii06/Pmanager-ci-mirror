## Spec v1.0 PR 03 — Quarantine Delete Engine

- Schema `v17`: added `file_mutations` (kind, request key, requested file version, state, resume state, quarantine root/rel, manifest, attempts, retry/lease fields, error fields), `mutation_events`, and `assets.pending_delete_mutation_id` with a partial index. The engine stays behind `FILE_MUTATION_ENGINE_ENABLED`; the API returns `503` and `DELETE /api/assets/:id` only queues while it is off.
- Delete state machine: `requested -> validated -> quarantined -> db_committed -> purging -> completed`, plus `failed_retryable`, `blocked`, and `cancelled_pre_commit`. Every transition is a lease-fenced compare-and-set (`lease_owner`, `lease_epoch`, `lease_expires_at`) that also writes a `mutation_events` row.
- The asset tombstone is the mutation's ownership marker. `touchAssets` and `updateAssetFile` now refuse a row with `pending_delete_mutation_id`, so a scan that still sees the file cannot clear `deleted_at` and resurrect it; `commitPermanentDelete` refuses a mismatched owner.
- Quarantine placement reads `/proc/self/mountinfo` and picks the longest mount that contains both the source and the media root, because two bind mounts of one disk share `st_dev` yet `rename(2)` returns `EXDEV`. No match falls back to a device walk. The quarantine directory is `.mediavault-quarantine` with mode `0o700`, and an `EXDEV` rename blocks the delete instead of copying.
- Validation before moving: asset exists and is not owned by another mutation, file version matches, library is `ONLINE`, the resolved source stays inside the library, it is a regular file (not a symlink), and its size and mtime match the index. The manifest records dev/ino/size/mtime plus the cache plan.

The web Watch page keeps one request key per asset, polls the operation, and only drops the asset from caches after completion.

## Spec v1.0 PR 06 — Idempotent Playback and Resume Race

- Schema `v20`: added `play_sessions` (user, asset, `file_version`, `client_session_key`, `started_at`/`ended_at`/`view_recorded_at`, `last_seq`, `UNIQUE(user_id, client_session_key)`) and `play_events` (`event_id` primary key, session, contiguous `seq`, type `watch_time|progress|view`, delta/position/duration, client and server timestamps, `UNIQUE(session_id, seq)`). `playback_progress` gained `file_version`, `progress_version`, `last_session_id` and `last_seq`, and every existing row was backfilled from its asset version (`191/191` on the live clone).
- `packages/database/src/playback.ts` was rewritten around one immediate transaction per event. `applyPlayEvent` resolves the session, loads the asset, normalizes the payload, returns a stored event as a duplicate (or an `event_id_conflict` when the payload changed), rejects an old `file_version`, then enforces `seq === last_seq + 1` (`sequence_gap` with `expectedSeq`) and `UNIQUE(session_id, seq)` (`sequence_conflict`) before inserting, bumping `last_seq`, and applying the side effect. A duplicate never re-aggregates.
- A view is recorded once per session through `UPDATE play_sessions SET view_recorded_at = ? WHERE id = ? AND view_recorded_at IS NULL`, and the aggregate only moves when that update returned a row. `watch_time_ms` accumulates per event; `progress` stores the server clock in `progress_version`.
